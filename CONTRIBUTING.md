# Maintaining OmegaConf release lines

This feedstock publishes each OmegaConf release line from its matching branch,
using the names of [OmegaConf's upstream release branches](https://github.com/hydra-ecosystem/omegaconf/branches):

| Feedstock branch | Release line | Purpose |
| --- | --- | --- |
| `main` | None | Bot configuration and release-line coordination; package uploads are disabled. |
| `2.3_branch` | 2.3.x | All 2.3 releases and rebuilds. |
| `2.4_branch` | 2.4.x | All 2.4 releases and rebuilds, including 2.4.0. |

The branches contain conda recipes for published source archives; they do not
automatically synchronize with upstream Git branches. OmegaConf 2.4 packages
support Python 3.10 and newer. The explicit `python_min` in that recipe preserves
this minimum even when conda-forge's default build variant moves forward.

## Updating a release line

1. Create a working branch in your fork from the matching feedstock release
   branch: `2.3_branch` for 2.3.x or `2.4_branch` for 2.4.x.
2. Update `recipe/meta.yaml` to the published release's version, source URL,
   checksum, and dependencies. Reset the build number to zero for a new version;
   increment it when rebuilding the same version.
3. Check the `channel_targets` override in `recipe/conda_build_config.yaml`
   against the intended publication label. Stable inputs currently omit this
   key and inherit `conda-forge main`; release candidates must set it
   explicitly to `conda-forge omegaconf_rc`.
4. Rerender with `conda smithy rerender`, verify the effective
   `channel_targets` in generated `.ci_support`, and validate locally with
   `python build-locally.py linux_64_`.
5. Open a PR from your fork targeting that same release branch. Check that CI
   passes before merging. Do not target `main` for releases or recipe rebuilds.

Each release branch sets `upload_on_branch` to its own name. After a release PR
merges, the branch build uploads to its configured channel target. Stable
releases use the shared `conda-forge` channel; release candidates use the
package-specific `omegaconf_rc` label. Versions, build numbers, and labels
distinguish the artifacts; branches do not inherently create separate channels.
Submit changes from forks rather than pushing directly to the feedstock. Updates to `main` are not automatically copied to release branches.

## Prerelease publication

Hydra and OmegaConf follow the same prerelease policy: a release candidate
builds from its matching release-line branch and publishes only to its
package-specific `_rc` label. For OmegaConf this is `omegaconf_rc`; Hydra uses
`hydra-core_rc`. Stable releases build from those same branches and publish
to the normal channel. This follows the
[conda-forge prerelease guidance](https://conda-forge.org/docs/maintainer/knowledge_base/#pre-release-builds).

For a future OmegaConf release candidate, set the following in
`recipe/conda_build_config.yaml` on the appropriate release branch:

```yaml
channel_targets:
  - conda-forge omegaconf_rc
```

Rerender and verify that the effective `channel_targets` in generated
`.ci_support` contains that target. Testers can opt into the prerelease
channel with `-c conda-forge/label/omegaconf_rc -c conda-forge` and an
explicit release-candidate version.

When preparing the stable release, update the version, published source,
checksum, and build number. Stable inputs with no `channel_targets` override
inherit `conda-forge main`; when promoting an RC to stable, replace the
explicit `omegaconf_rc` override with `channel_targets: [conda-forge main]`
in the same PR. Keep `upload_on_branch` pointing at the release-line branch,
rerender, and verify the effective target in generated `.ci_support` before
merging. This changes the target for new builds; it does not relabel
previously published packages.

Applying this policy to a future prerelease requires the recipe change above;
documentation alone does not change an upload target.

## Bot migrations and branch lifecycle

The bot reads its configuration from `conda-forge.yml` on `main`.
`bot.abi_migration_branches` lists `2.3_branch` and `2.4_branch` so they receive
migration PRs. `bot.version_updates.skip: true` disables version-update PRs to
`main`; maintainers submit new versions manually to the appropriate release
branch. Migration-branch configuration does not automate patch-version updates.

For a future release line, follow conda-forge's
[multiple-version maintenance guide](https://conda-forge.org/docs/how-to/advanced/several-versions/):
create a branch from the relevant recipe with an empty `[ci skip]` commit before
the initial push. Configure its `github.branch_name` and `upload_on_branch` to
match the new branch, and add it to the migration list on `main`. Submit the
first release through a PR to that branch. Remove a retired line from the list
to stop migration PRs.

The top-level README is generated by conda-smithy. Its branch-aware publishing
paragraph is maintained in `templates/README.md.tmpl`; preserve that override
when refreshing conda-smithy and rerender each release-line branch. Keep
release-line maintenance instructions in this file so rerendering preserves
them.

## Native CI builds

`templates/github-actions.yml.tmpl` is based on conda-smithy 2026.9.23. It
registers QEMU only when the build and target platforms differ. Native builds
therefore avoid an unnecessary Docker Hub pull and its shared rate limit. When
updating conda-smithy, refresh this template from that version and preserve the
`EMULATED` matrix field and emulator-step condition before rerendering.
