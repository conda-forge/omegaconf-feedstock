# Maintaining OmegaConf release lines

This feedstock maintains the following branches, matching the names of
[OmegaConf's upstream release branches](https://github.com/hydra-ecosystem/omegaconf/branches):

| Feedstock branch | Release line | Purpose |
| --- | --- | --- |
| `main` | Latest stable release | Default target for new stable releases. |
| `2.3_branch` | 2.3.x | Patch releases and rebuilds for the 2.3 line. |
| `2.4_branch` | 2.4.x | Patch releases and rebuilds for the 2.4 line. |

The branches contain conda recipes for published source archives; they do not
automatically synchronize with upstream Git branches. OmegaConf 2.4 packages
support Python 3.10 and newer. The explicit `python_min` in the recipe preserves
that minimum even when conda-forge's default build variant moves forward.

## Updating a release line

1. Create a working branch in your fork from the intended feedstock branch.
2. Update `recipe/meta.yaml` to the published release's version, source URL,
   checksum, and dependencies. Reset the build number to zero for a new version;
   increment it when rebuilding the same version.
3. Rerender with `conda smithy rerender` and validate locally with
   `python build-locally.py linux_64_`.
4. Open a PR from your fork targeting the matching feedstock branch. Check that
   CI passes before merging.

While `main` and a release branch track the same version, carry applicable
recipe fixes to both through separate PRs. Coordinate their build numbers so
they produce distinct package builds. Changes merged into `main` are not
automatically copied to the release branches.

Pushes to feedstock branches normally build and upload packages to the same
`conda-forge` channel. The package version and build identify each artifact;
release branches do not create separate channels. Submit normal changes from
forks rather than pushing directly to the feedstock.

## Bot migrations and branch lifecycle

`bot.abi_migration_branches` in `conda-forge.yml` on `main` lists `2.3_branch`
and `2.4_branch`. Once that configuration is merged, the branches are eligible
for migration PRs. This setting does not enable automatic patch-version
updates; maintainers must submit those PRs themselves.

For a future release line, follow conda-forge's
[multiple-version maintenance guide](https://conda-forge.org/docs/how-to/advanced/several-versions/):
branch from the relevant successfully published recipe, create an empty
`[ci skip]` commit before the initial push, and add the branch to the migration
list on `main`. Remove a retired line from that list to stop migration PRs.

The top-level README is generated by conda-smithy. Keep release-line
maintenance instructions in this file so rerendering preserves them.
